Electron release review · MIT

Know what changed inside your Electron release.

Give hexvero the build you shipped and the one you are about to ship. It lists the IPC channels, preload members, window settings and hosts that changed, points at the line in both builds, and fails CI when a change breaks your policy. Neither build is run.

~Changed, and in which direction

nodeIntegration on → off, sandbox off → on: reported as less permissive. The same change the other way fails window-more-permissive.

?Unknown is not removed

shell:open exists only in 1.4.0, but 1.5.0 registers channels named from an environment variable (main.js:33). It may be one of them, so it is reported as unknown, with the reason.

+A fact, not a verdict

A static finding says what the code contains. It does not show that the code runs, or that anything is exploitable. That judgement stays with the reviewer.

$ hexvero check … --policy .hexvero/policy.json

A release gate that fails on what changed, not on what was always there.

A JSON policy over the comparison: new preload member, new external host, more permissive window, weakened fuse, new openExternal, a permission handler that grants everything, a weaker CSP. Accept today's state once with a baseline; later runs fail only on new findings.

One build, the checks people know from Electronegativity.

Electronegativity, Doyensec's open-source checker, has been archived since 2026-10-24; its last npm release is from March 2023. hexvero audit reads one packaged build with the same exit codes and SARIF as check. It covers part of Electronegativity's checks, not all of them, and the list below says which.

Every row, with its Electronegativity check id: docs/engineering/audit-plan.md. Baselines and suppressions work as in check. ElectroNG is Doyensec's commercial successor; hexvero is not affiliated with Doyensec.

Open Electronegativity issues, and what hexvero does

  • #113 Packaged, minified .app reported as having no CSP: hexvero opens the .app, a directory or the ZIP and reads bundled and minified code by scope.
  • #108 An exit code when issues are found: 0, 3, 4, as in check.
  • #106 Unknown Electron release breaks the run: an unknown line is reported as unknown, not as an error.
  • #93 Suppression comments broken by Prettier: fingerprints name the item, never the line.
  • #58 Old webPreferences defaults assumed: defaults follow the Electron major in package.json, and say so.

Which tool for which question

Compared with REA and Electronegativity.

Different tools answer different questions. If you want to know how a feature of someone else's app works, down to decompiled functions and run-time traffic, REA is built for that. If you need to know what your release changed and whether it may ship, that is the job hexvero is built around.

Question hexvero 0.13 REA Electronegativity
Main question What changed between two Electron builds, and may it ship? How does this app work, and how can an agent rebuild it? Which known anti-patterns does this code contain?
Runs the target never, by design static by default; runtime capture runs or interacts with it no
Two-version comparison per list, file and line in both builds documented (compare_application_versions) Electron API upgrade checks only
Preload → channel → handler map with how each link was read documented IPC and bridge tracing not found
Release policy, baseline, suppressions hexvero check not found in its docs per-line comments
SARIF 2.1.0 not found in its docs yes
Decompiler and runtime capture no (radare2, rizin or Ghidra if installed) Hopper, Ghidra, IDA; browser, process, adb no
Maintained yes yes archived 2026-10-24

REA and Electronegativity cells come from their own documentation, read 2026-10-17; Electronegativity's archive status checked 2026-10-31. "Not found" means their docs did not show it, which is not proof it is absent. Details and measurements on the same inputs: docs/comparison.md.

$ hexvero ui --demo --open

The same review in a local UI, a report, or your coding agent.

The UI binds to 127.0.0.1 with a per-session token and loads nothing from the network. The HTML report is one offline file. The MCP server gives an agent the same comparison and the same policy in small, paged answers. 

$ npx hexvero setup --apply          # register the MCP server
$ npx hexvero setup --skill --apply  # install the skill

16 tools, including hexvero_check. Text read from a target is marked as data, not instructions. With a cloud-hosted agent, what the agent reads goes to its model provider.

Accuracy and limits

What it cannot tell you.

  • It reads files and never observes a running program. A finding is what the code contains, not what it does.
  • Values computed at run time are listed as unresolved, never guessed; an item they might hide is unknown, not removed.
  • It misses things. On a blind set written by someone without access to hexvero (measured once, 2026-10-17) it found 52 of 64 IPC channels with none false, and 22 of 41 storage keys.
  • Window settings were weaker on that set: 44 of 52, with 15 false rows, fixed after the measurement. Absence from a list is weaker evidence than presence.
  • Not executing the target is not a safety guarantee: parsing a hostile file still processes attacker-controlled bytes, within size, depth and time limits.
  • No disassembly without radare2, rizin or Ghidra installed, and no dynamic analysis.
