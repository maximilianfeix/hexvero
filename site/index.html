Inspect, compare, verify

For Electron developers and security engineers who need to know what a shipped app or an update actually contains, and for coding agents doing the same work.

  1. Inspect

    What a build exposes: IPC channels with senders and handlers, preload members, window settings, endpoints, storage keys. Native binaries get imports, libraries and hardening. 

    $ hexvero analyze notesdesk-1.5.0.asar
  ● 6 members exposed to pages as window.notesdesk  @ preload.js:4
  ○ 3 network endpoints read from the code  @ main.js:30

  2. Compare

    What the next release added, removed or changed, list by list. Code that only moved is not reported as changed. 

    $ hexvero compare notesdesk-1.4.0.asar notesdesk-1.5.0.asar
  collection      added  removed  changed
  contextBridge   1      1        0
  windows         0      0        1
  endpoints       1      0        0

  3. Verify

    Every change names the file and line it was read from, and whether it was read as written or inferred. What could not be established is listed. 

    $ hexvero compare a.asar b.asar --report report.md
  + update:check  @ b: receiver main.js:30, sender preload.js:9
✓ report.md

One change, with its evidence

From the example: release 1.5.0 adds an IPC channel whose handler fetches a URL.

  • Fact. main.js line 30 registers a handler for update:check; preload.js line 9 sends on it. Both were read from the archive as written.
  • Inference. A page can reach it as window.notesdesk.checkUpdate: the preload member and the handler use the same channel (link direct). Whether any page calls it is not something a static reading can show.
  • Open question. Line 33 registers channels whose names come from an environment variable. hexvero reports that (ipc_channel_unresolved) instead of guessing, and the IPC finding turns from confirmed to inferred.

A static finding says what the code contains. It does not show that the code runs, or that anything is exploitable.

CLI, local UI, and an MCP server for coding agents

CLI and UI

npx hexvero analyze ./MyApp.app/Contents/Resources/app.asar
npx hexvero compare old.asar new.asar --report report.md
npx hexvero ui --open

The UI binds to 127.0.0.1 with a per-session token. Fonts are bundled; nothing is loaded from the network.

MCP

npx hexvero setup --apply          # registers the server
npx hexvero setup --skill --apply  # installs the skill

Claude Code, Codex, Cursor, VS Code and 14 other clients. Answers are small pages with suggested next calls; text from the target is marked as data, not instructions. With a cloud-hosted agent, what the agent reads goes to its model provider.

What it reads, and what it cannot tell you

  • Electron ASAR and app folders
  • JavaScript bundles and source maps
  • ELF
  • PE
  • Mach-O and .app bundles
  • Go
  • .NET
  • Android APK and DEX
  • Java class and JAR
  • WebAssembly
  • SQLite, plist, ZIP, HAR
  • It reads files and never observes a running program. A finding is what the code contains, not what it does.
  • It misses things. On the newest blind set (an app written by someone without access to hexvero, measured once with 0.7.3) it found 12 of 57 IPC channels and 5 of 8 expected changes between two versions; most misses were channels built by a registry function it does not evaluate. Absence from a list is weaker evidence than presence.
  • Values computed at run time are shown as ${…} or listed as unresolved, never guessed.
  • Not executing the target is not a safety guarantee: parsing a hostile file still processes attacker-controlled bytes, within size, depth and time limits.
  • No disassembly without radare2, rizin or Ghidra; no dynamic analysis.
