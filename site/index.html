Know what changed inside your Electron release.

The interfaces pages can call, window settings and network hosts that changed between two builds, with the file and line on both sides, what could not be established, and a policy gate for CI. Locally, without executing the target.

One change, with its evidence

From the example: release 1.5.0 adds an IPC channel whose handler fetches a URL.

  • Fact. main.js line 30 registers a handler for update:check; preload.js line 9 sends on it. Both were read from the archive as written.
  • Inference. A page can reach it as window.notesdesk.checkUpdate: the preload member and the handler use the same channel (link direct). Whether any page calls it is not something a static reading can show.
  • Unknown, not removed. 1.5.0 registers channels whose names come from an environment variable (main.js:33, ipc_channel_unresolved). So shell:open, present only in 1.4.0, is reported as unknown: the other build has a channel there that could not be named.

The release gate

hexvero check applies a policy to the comparison of the build you shipped and the build you are about to ship. A real run on the example builds: 

$ hexvero check hexvero-demo/notesdesk-1.4.0.asar hexvero-demo/notesdesk-1.5.0.asar --policy hexvero-demo/policy.json
hexvero check fail: the policy is violated
  before notesdesk-1.4.0.asar · after notesdesk-1.5.0.asar · policy policy.json

  ✗ new-interface-member  notesdesk.checkUpdate  new · fail
      New interface member notesdesk.checkUpdate is exposed to pages.
      @ b: preload.js:9, handler main.js:30 · link direct · fingerprint 40aa15f76bfd9988f9302d187c03c61d
  ✗ new-external-host  updates.notesdesk.example  new · fail
      New external host updates.notesdesk.example, not in the allow list (https://updates.notesdesk.example/latest.json).
      @ b: main.js:30 · literal · fingerprint 68312dcec55422c3b8affec165b21b83

  Accept what is there now: add --baseline <file> --update-baseline, or a suppression with the fingerprint and a reason in the policy.

Exit 3. After --baseline .hexvero/baseline.json --update-baseline accepts the two findings, the same run exits 0. Exit codes: 0 pass, 1 technical error, 2 usage or invalid policy, 3 violated, 4 not decidable (an unknown under "unknown": "fail"). Output as text, JSON, Markdown or SARIF 2.1.0.

In GitHub Actions

From docs/ci.md: the check job with contents: read, the SARIF upload as a separate job with security-events: write, skipped for pull requests from forks. hexvero check is in hexvero 0.9.0 and later. 

name: Release policy

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7
        with:
          persist-credentials: false
      - uses: actions/setup-node@949feb2413d6458794dcd2491c4babbbce0c15c1 # v7
        with:
          node-version: 24
      # Build your app and fetch the previous release here, e.g. into previous/ and dist/.
      - name: hexvero check
        run: |
          set +e
          npx --yes hexvero@0.9.1 check previous/app.asar dist/app.asar \
            --policy .hexvero/policy.json --baseline .hexvero/baseline.json \
            --format sarif --out hexvero.sarif
          code=$?
          set -e
          npx --yes hexvero@0.9.1 check previous/app.asar dist/app.asar \
            --policy .hexvero/policy.json --baseline .hexvero/baseline.json \
            --format markdown >> "$GITHUB_STEP_SUMMARY" || true
          exit "$code"
      - if: always()
        uses: actions/upload-artifact@ea165f8d65b6e75b540449e92b4886f43607fa02 # v4
        with:
          name: hexvero-sarif
          path: hexvero.sarif
          if-no-files-found: ignore

  upload:
    needs: check
    if: >-
      always() &&
      (github.event_name != 'pull_request' ||
       github.event.pull_request.head.repo.full_name == github.repository)
    runs-on: ubuntu-latest
    permissions:
      contents: read
      security-events: write
    steps:
      - uses: actions/download-artifact@d3f86a106a0bac45b974a628896c90dbdf5c8093 # v4
        with:
          name: hexvero-sarif
      - uses: github/codeql-action/upload-sarif@b96794f015dfd88f77b49b1c93e0fa7110f94c63 # v4.38.0
        with:
          sarif_file: hexvero.sarif
          category: hexvero-check

A pass means hexvero found nothing new against the policy in what it read. It is not a proof that the app cannot do these things at run time. SARIF locations are paths inside the analyzed build (hexvero-build/after/…), never mapped onto your sources.

CLI, local UI, and an MCP server for coding agents

CLI and UI

npx hexvero compare old.asar new.asar --report report.html
npx hexvero check old.asar new.asar --policy policy.json
npx hexvero ui --demo --open

The UI binds to 127.0.0.1 with a per-session token. Fonts are bundled; nothing is loaded from the network. The HTML report is one offline file.

MCP

npx hexvero setup --apply          # registers the server
npx hexvero setup --skill --apply  # installs the skill

16 tools, including hexvero_check for the same policy. Answers are small pages with suggested next calls; text from the target is marked as data, not instructions. With a cloud-hosted agent, what the agent reads goes to its model provider.

What it reads, and what it cannot tell you

  • Electron ASAR (with app.asar.unpacked) and app folders
  • JavaScript bundles and source maps
  • ELF
  • PE
  • Mach-O and .app bundles
  • Go
  • .NET
  • Android APK and DEX
  • Java class and JAR
  • WebAssembly
  • SQLite, plist, ZIP, HAR
  • It reads files and never observes a running program. A finding is what the code contains, not what it does, and not whether anything is exploitable.
  • It misses things. On the newest blind set (one app in three builds, written by someone without access to hexvero, measured once on 2026-10-17) it found 49 of 54 IPC channels with none false, but only 14 of 39 window settings, and of the changes to the next version 3 of 4 channels, 4 of 4 bridge members, 0 of 2 window settings and 1 of 1 endpoint. Most misses: a wrapper class around ipcMain and window options built with Object.assign. Absence from a list is weaker evidence than presence.
  • Since then wrapper classes are read. On the same set, now a development set and not a blind result: 72 of 72 IPC channels, but window settings still 17 of 52. On Electron Fiddle 0.38.0 and 0.39.0, which registers handlers through ipcMainManager.handle, 45 of 46 bridge members are now linked to a main-process handler (0.8.0: none).
  • Values computed at run time are shown as ${…} or listed as unresolved, never guessed; an item they might hide is unknown, not removed.
  • Not executing the target is not a safety guarantee: parsing a hostile file still processes attacker-controlled bytes, within size, depth and time limits.
  • No disassembly without radare2, rizin or Ghidra; no dynamic analysis.
