**The first look at a binary or app bundle: static facts with the evidence next to them, from Node alone.** hexvero reads executables, app bundles, archives, databases and captures on your machine **without executing them** and tells you what it found, where it read it, how sure it is, and what it could not establish. One CLI, one 15-tool MCP server for coding agents, one local web UI. Engines are optional.

![hexvero analyzing an Electron app in the terminal: findings with file and line, the IPC call sites of one channel, and the settings that changed between two builds](docs/demo/demo.gif)

```bash
npx hexvero analyze ./app.asar          # what is it, what does it expose, where is the evidence
npx hexvero ui --open                   # the same in a local browser UI with hex view and module graph
npx hexvero setup --apply               # register the MCP server with the agent clients on this machine
```

The comparison with REA below was measured on `main`. To run `main` today: `git clone`, `npm install`, `npm run build`, `node packages/cli/bin/hexvero.js`.

## Three things you can do in a minute

The inputs ship in [`examples/`](examples/) and are generated by [`scripts/build-examples.mjs`](scripts/build-examples.mjs): a small Electron note-taking app and a small C program, each in two versions, written for these demos (MIT). The outputs below are real runs, trimmed only where marked; `npm run e2e` asserts them on every change. The recording above is produced by [`docs/demo/demo.tape`](docs/demo/demo.tape).

> The outputs in this section are from the development version after 0.3.0 and are **not released yet**. `hexvero@0.3.0` from npm prints fewer findings, has no `windows` collection and misses IPC calls made through a renamed `ipcMain`/`ipcRenderer`; see [CHANGELOG.md](CHANGELOG.md), "Unreleased".

**1. List what an Electron app exposes, with the line each fact came from**

```text
$ hexvero analyze examples/notesdesk-1.4.0.asar
examples/notesdesk-1.4.0.asar
  asar · 6.1 KiB (6222 bytes) · sha256 875c2bb7fb7eebcd… · 11 ms

Summary
  Electron ASAR: 4 JavaScript modules, 6 IPC channels

Findings
  ○ nodeIntegration: true in a BrowserWindow  @ main.js:14
      contextIsolation is on for the same window, so page scripts do not get require(). Node integration keeps the renderer out of the Chromium sandbox.
  ○ sandbox: false in a BrowserWindow  @ main.js:15
      The renderer process runs without the Chromium sandbox.
  ● 6 IPC channels  @ main.js:25
      app:quit, notes:list, notes:save, settings:get, settings:set, shell:open (collections ipcChannels, ipc)
  ● 6 members exposed to pages as window.notesdesk  @ preload.js:4
      getSetting, setSetting, listNotes, saveNote, quit, openInShell (collection contextBridge)
  ○ 1 preload script  @ main.js:12
      preload.js
  ○ 2 network endpoints read from the code  @ renderer/app.bundle.js:11
      ${…}/notes/sync, https://telemetry.notesdesk.example/collect (collection endpoints)
  ● 1 storage key read from the code  @ renderer/app.bundle.js:10
      notesdesk.token (collection storage)
  … (list of collections)

$ hexvero collection examples/notesdesk-1.4.0.asar ipc --text shell:open
ipc 1-2 of 2
  module      api               channel     line
  ----------  ----------------  ----------  ----
  main.js     ipcMain.on        shell:open  30
  preload.js  ipcRenderer.send  shell:open  9
```

A filled dot is a fact read from the file; a hollow dot is an inference from a pattern. Settings are reported as written in the source (`webPreferences` collection). The `windows` collection puts each window's `nodeIntegration`, `contextIsolation` and `sandbox` side by side as `true`, `false`, `computed` or `not written`, and says what follows from them together. A value that rests on Electron's default for the version `package.json` asks for is marked `default on` / `default off`, never `on` / `off`: that version is the app's own metadata, not the runtime it ships. The rules and their sources are in [docs/electron-findings.md](docs/electron-findings.md). The IPC finding is a filled dot only when every IPC-shaped call could be traced and every channel read; otherwise the limitations name the calls that could not, with file and line.

**2. See what a native binary is, and who calls what**

```text
$ cc -O0 -o demo examples/native/demo-v2.c
$ hexvero collection demo imports
imports 1-5 of 5
  name
  -------
  _getenv
  _printf
  _puts
  _strlen
  _system

$ hexvero calls demo radare2 main --goal system
radare2 path main → sym.imp.system · found
main
  └ sym._run_tool
    └ sym.imp.system
```

Imports, libraries, symbols, sections and hardening facts (NX, PIE, RELRO, canaries, FORTIFY; ASLR, CFG, GS, Authenticode; code signature) come from hexvero's own parsers. Call graphs and cross-references come from radare2, rizin or Ghidra when one is installed. Tail calls are part of the graph through radare2 and rizin; where an engine's jump list is cut or unreadable, the result carries a limitation instead of a definite "not reached".

**3. Explain what changed between two builds**

```text
$ hexvero compare examples/notesdesk-1.4.0.asar examples/notesdesk-1.5.0.asar ipcChannels
ipcChannels: 1 added, 1 removed, 0 changed, 5 unchanged · matched by channel
  + update:check
  - shell:open

$ hexvero compare examples/notesdesk-1.4.0.asar examples/notesdesk-1.5.0.asar webPreferences
webPreferences: 0 added, 0 removed, 2 changed, 2 unchanged · matched by file+windowName+key
  ~ main.js::win::nodeIntegration  value: true → false
  ~ main.js::win::sandbox  value: false → true

$ hexvero compare examples/notesdesk-1.4.0.asar examples/notesdesk-1.5.0.asar windows
windows: 0 added, 0 removed, 1 changed, 0 unchanged · matched by file+windowName
  ~ main.js::win  nodeIntegration: true → false, nodeIntegrationInEffect: "on" → "off", sandbox: false → true, sandboxInEffect: "off" → "on"

$ hexvero compare demo-v1 demo-v2 symbols
symbols: 3 added, 0 removed, 0 changed, 6 unchanged, 2 relocated · matched by name
  + _read_config
  + _getenv
  + _strlen
  2 item(s) only moved (value changed, e.g. _main value "0x100000588" → "0x1000005fc"); --strict counts them as changed
```

Nothing is ignored by default. The one built-in rule: in native binaries a symbol or section whose only difference is its address is counted as `relocated` and shown with an example; a value that changes from `old` to `new` is always a change. The output says when a comparison is partial. Window settings are matched by the variable the window is assigned to (`win`), so a window added before another does not pair two different windows; a window without a name is matched by its position in the file, and the output says how many were. An item found on one side only is `added` or `removed` only if the other side read the file it sits in; otherwise it is listed as `unknown` (`?`).

### Why hexvero

- **Zero-dependency parsers, any OS.** Every format listed below is parsed by code in this repository. No JDK, no Python, no engine, and no file is ever executed.
- **Bounded by design.** Every list is a page with a hard byte budget (`maxBytes`, default 256 KiB, measured on the real serialized size) and a `next` offset. A 541 MiB Electron app answers `analyze` over MCP in a 15 KB result ([benchmarks](docs/benchmarks.md)). The complete result goes to a file with one command, never into a context window.
- **Evidence and honesty.** Findings carry `confirmed` or `inferred` and, where a parser records it, the file and line; `limitations` say what was skipped, truncated or unreadable and why; an unknowns ledger keeps open questions.
- **Measured, not claimed.** A [corpus](corpus/README.md) with written-down correct results says per kind of finding what is found, missed and wrongly reported, including on a set hexvero was never tuned on; CI fails when a result gets worse.
- **15 tools, 13.7 KB catalog.** The MCP server reads like a workflow: open, analyze, page, read bytes, compare, recover, export.
- **A local UI.** Verdict, findings, virtualized tables, a hex viewer with live decoding, a module graph for Electron apps. Keyboard-usable, loopback only.
- **Engines when you want them.** radare2, rizin and Ghidra plug in behind one interface for disassembly, decompilation, cross-references and cached call graphs.

<a id="install"></a>

## Install

Requires Node.js 22.12 or newer (24 recommended for SQLite support without warnings).

```bash
npm install -g hexvero        # the hexvero command
hexvero doctor                # checks Node, node:sqlite and optional engines
```

Or run without installing: `npx hexvero <command>`.

## What it reads

Everything in this table works with Node alone. Engines add disassembly and decompilation on top.

| Target                   | Built-in result                                                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| ELF (32/64, LE/BE)       | Sections, segments, symbols, dynamic imports/exports, needed libraries, RPATH, build-id, NX/PIE/RELRO/canary/FORTIFY            |
| PE / PE32+               | Sections with entropy, imports (names and ordinals), exports and forwarders, PDB path, VERSIONINFO, ASLR/NX/CFG/GS/Authenticode |
| Mach-O (thin and fat)    | Load commands, segments, symbols, dylibs, UUID, platform/SDK, encryption, code signature, PIE/ARC/canary                        |
| Apple `.app` bundles     | Info.plist facts, executable, frameworks, entitlements, Objective-C classes/protocols, readable Swift names                     |
| Go binaries              | Compiler version, main module, dependencies with replacements, build settings, VCS revision                                     |
| .NET assemblies          | Assembly and references, types with methods, P/Invoke, user strings, CIL method bodies with call targets and digests            |
| Rust / C / C++ toolchain | Compiler and rustc version strings, DWARF presence, build paths (confirmed only when a version string is present)               |
| WebAssembly              | Types, imports/exports with correct index spaces, memories, tables, producers, WASI/Emscripten/wasm-bindgen                     |
| EVM bytecode             | PUSH-aware disassembly, dispatch selectors with jump targets, solc metadata, DELEGATECALL/SELFDESTRUCT                          |
| SQLite databases         | Tables, columns, row counts, sample rows, views, indexes, triggers (read-only via `node:sqlite`)                                |
| plist (XML and binary)   | Fully decoded property list                                                                                                     |
| Android APK              | Manifest, permissions, components with intent filters, deep links, native libs, DEX classes, resources.arsc, frameworks         |
| Java class / JAR / DEX   | Constant pool, members, referenced APIs, manifest and packages; DEX classes, strings and SDK hints                              |
| Flutter apps             | Engine and Dart snapshot facts, library digests                                                                                 |
| Electron ASAR / JS apps  | Package facts, module roles, resolved import graph, IPC channel sender/receiver matching, preload and `webPreferences` flags    |
| JavaScript bundles       | webpack / Rspack / browserify / esbuild module boundaries, requires, exports, endpoints, storage, vendor fingerprints           |
| Source maps              | Sources grouped by package, mapping count, original position lookup, originals written back to disk                             |
| ZIP, HAR                 | ZIP/ZIP64 entries; HAR hosts, methods, status buckets, API-like endpoints, secrets in URLs, auth headers, WebSockets            |
| Anything                 | Strings (ASCII and UTF-16) with tags, bounded byte windows, entropy                                                             |

<a id="cli"></a>

## CLI

```text
hexvero analyze <path> [--json] [--out file.json]     summary, findings, limitations, overview
hexvero collection <path> <name> [--text s] [--limit n] [--offset n] [--max-bytes n]
hexvero strings <path> [--min n] [--utf16] [--tag url|path|email|ip|format|secret-ish|base64-ish]
hexvero bytes <path> <offset> [length]                hex dump (64 KiB per call)
hexvero compare <a> <b> <collection> [--key f[+g]] [--ignore f,g] [--strict]
                                                      added, removed, changed and relocated items between two builds
hexvero export <path> <out.json>                      the complete analysis
hexvero recover <bundle.js|map> <outdir>              split one JS bundle into module files, or write a source map's originals
hexvero provider <path> radare2|rizin|ghidra <op> [--address a] [--text s]
                                                      functions, disassemble, decompile, strings, imports,
                                                      xrefs, callers, callees, callgraph, search
hexvero calls <path> <engine> <root> [--direction callers|callees|both] [--depth n] [--goal g]
hexvero mcp · hexvero ui [--port n] [--open] · hexvero doctor · hexvero setup [--client c] [--apply] [--all]
```

Analysis commands take `--json`. Exit codes: `0` ok (including `--help`), `1` analysis failed (with a structured error), `2` usage. See [docs/cli.md](docs/cli.md).

## Web UI

```bash
hexvero ui --open
```

![hexvero UI: the overview of an Electron app, each finding with its confidence and source line](docs/screenshots/ui-overview.png)

![hexvero UI: findings with their source lines, and the hex viewer decoding a selected byte](docs/screenshots/ui-hex.png)

Starts a loopback server with a per-session token and opens the browser. Drop a file anywhere, or type a path on your machine. Each target gets a verdict line, a fact sheet, findings with confidence, the limitations, and one tab per collection that actually exists. The hex viewer loads windows on demand, decodes the selected bytes as u8…u64/f32/f64 in both byte orders and follows the arrow keys. Electron apps get a layered module graph. Dark and light themes, keyboard navigation throughout (`⌘O`/`Ctrl+O` open, `/` filter, arrow keys on tabs, hex and graph), phone layout.

## For AI agents

```bash
hexvero setup                 # shows what would change (dry run)
hexvero setup --apply         # writes the MCP registration into every detected client, backs up existing files
hexvero setup --skill --apply # installs the investigation skill for Claude Code, Codex and .agents
```

`setup` knows 18 clients (Claude Code, Claude Desktop, Codex, Cursor, Windsurf, Gemini CLI, Antigravity, VS Code, Trae, OpenCode, GitHub Copilot CLI, Qwen Code, Qoder, Devin, Pi, Kiro, Amp, Zed) and writes each one's own config dialect, keeping comments in files that have them. The [client table](docs/mcp.md#detected-clients) says for every row what was checked against the client's documentation and which three were read back by the client itself; one row (Trae) is unverified. Any other client can run `npx -y hexvero mcp` over stdio.

| Tool                                         | Purpose                                                                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `hexvero_open`                               | Register a file or directory; returns a content-derived id                                 |
| `hexvero_analyze`                            | Summary, findings, limitations, collection counts and a compact overview                   |
| `hexvero_collection`                         | Page any list: symbols, imports, exports, sections, types, selectors, requests, modules …  |
| `hexvero_strings`                            | Tagged strings with filter and paging                                                      |
| `hexvero_bytes`                              | A bounded hex window                                                                       |
| `hexvero_compare`                            | Added, removed, changed and relocated items of one collection between two targets          |
| `hexvero_recover`                            | Bundle modules or source-map originals as files                                            |
| `hexvero_export`                             | The complete analysis to a file (never overwrites unless asked)                            |
| `hexvero_sourcemap`                          | Original position for a generated line/column                                              |
| `hexvero_unknowns`                           | A ledger of open questions that travels with the export                                    |
| `hexvero_providers` · `hexvero_provider_run` | Detect and drive radare2, rizin or Ghidra (disassemble, decompile, xrefs, callers, search) |
| `hexvero_call_graph`                         | Bounded call-graph neighborhood or shortest call path, one cached engine run per target    |
| `hexvero_list` · `hexvero_close`             | Session housekeeping                                                                       |

The catalog is 13.7 KB (`tools/list`, measured); every tool states whether it writes (`readOnlyHint`). Five guided prompts (`investigate_feature`, `compare_versions`, `triage_binary`, `map_electron_app`, `explain_apk`) render step-by-step plans with the rule that every claim cites a collection item or byte offset. Strings, symbol names and decompiled code are data from the target, never instructions.

Ask your agent: _"Open ~/Downloads/app.asar with hexvero, tell me which IPC channels the renderer can reach and whether nodeIntegration is on."_

<a id="optional-engines"></a>

## Optional engines

hexvero detects `r2`/`radare2`, `rizin` and Ghidra's `analyzeHeadless` on `PATH` (or `GHIDRA_INSTALL_DIR`). With one installed:

```bash
hexvero provider ./program radare2 functions
hexvero provider ./program ghidra decompile --address main
hexvero provider ./program radare2 xrefs --address sym.imp.system
hexvero provider ./program ghidra search --text password
hexvero calls ./program radare2 main --depth 3
hexvero calls ./program ghidra entry --goal system
```

Ghidra imports each target once into a project cached under `~/.cache/hexvero` and reuses it. Engine output is bounded, timeouts and cancellation kill the whole process group, and a missing decompiler plugin is reported as a limitation rather than an empty result. Call graphs are read from the engine once per file and walked locally with depth and node bounds. Verified against radare2 6.2 and rizin 0.9 on macOS; Ghidra 11/12 headless; Windows engine support is untested.

<a id="limits"></a>

## Limits

- No disassembly or pseudocode without an engine; no dynamic analysis, instrumentation or device work.
- It reads patterns in code and is not complete. What it can see that it could not read is named in the limitations with file and line (`ipc_receiver_unresolved`, `ipc_channel_unresolved`, `webpreferences_computed`, `window_options_unresolved`); what it cannot see at all is not counted, so no result here is a coverage figure.
- IPC is found on `ipcMain`/`ipcRenderer`, on other names bound to them in the same file, on a `window.` global of the page, and on a name bound at the top of a file in the same directory when nothing imports the using file (the shape of a main process that is built into one script). Not followed: an application's own wrapper method around IPC (`manager.handle(channel, fn)` on an object), channels passed as a function parameter or iterated from an array, and names defined in files that were not read.
- Channel names are followed from literals, top-level constants and tables, and compiled TypeScript string enums. A minifier's one-letter local for an enum is not followed outside its function.
- Window settings: ten `webPreferences` keys are read where they are written in a window's options, in an object spread into them, or in a helper function that returns them. A value that is not a literal is listed as `computed` with its expression. Electron fuses, CSP, navigation and permission handlers and sender validation in IPC handlers are not checked, and nothing is rated by severity.
- The derived columns of `windows` follow Electron's documented rules for the settings as written. They do not know the Electron version that is actually shipped, command-line switches, or settings changed at run time.
- JavaScript apps are read 5,000 files at a time; `analyze --continue`, `--all` or `--include` reads more, and a partial result says so. Very large single items are returned compacted with a marker.
- A request whose address comes from a function parameter cannot be read. Constants are followed only from the top level of a file.
- `compare` is a per-collection diff: it does not line up renamed functions or match by structure. A window that was renamed shows up as removed and added.
- Findings carry a file and line for Electron apps (line 1 on minified bundles; IPC rows have no column); native findings cite a collection rather than an offset.
- Engine results are as good as the engine's analysis; hexvero verifies radare2 and rizin end to end, Ghidra through its headless script on fixtures only.
- Static facts are not proof of behaviour: an imported symbol or a matched string says what a file contains, not what it does at runtime.
- Files above 512 MiB are read lazily only for ASAR; other formats are refused with `too_large`.

<a id="compared-with-rea"></a>

## Compared with REA

[REA](https://github.com/morluto/rea) is the larger and older project in this space. hexvero is an independent implementation (no REA code) for the first look. The comparison below was run on 2026-10-13 on hexvero's [corpus](corpus/README.md), a set of small applications and programs whose correct results are written down, with hexvero at commit `a6d9b82` and REA 6.4.0 (`rea-agents` from npm), both on Node 24.21 on the same machine. Method, every mapping decision, the harness and the raw data of 1,460 runs are in [corpus/compare](corpus/compare/README.md).

Only the hold-out set is level ground: it was written without access to either tool and measured before hexvero was changed again. hexvero was tuned on the other two sets, so its near-perfect results there say little. Each cell is hit / missed / false, over the three builds of one Electron application (as written, bundled, minified):

| Hold-out set                        | hexvero     | REA 6.4.0                            |
| ----------------------------------- | ----------- | ------------------------------------ |
| IPC channels                        | 41 / 31 / 0 | 33 / 39 / 0                          |
| Window settings                     | 12 / 21 / 0 | 0 / 33 / 0                           |
| contextBridge members               | 60 / 9 / 0  | 0 / 69 / 0                           |
| Network endpoints                   | 24 / 18 / 5 | 9 / 33 / 30                          |
| Storage keys                        | 42 / 9 / 0  | 12 / 39 / 0                          |
| Changes between two builds, 5 lists | 7 / 11 / 2  | 0 / 18 / 1                           |
| Native call paths, two binaries     | 36 / 0 / 0  | not run: needs Ghidra, Hopper or IDA |
| Damaged inputs handled honestly     | 6 of 6      | 6 of 6                               |

What this shows, and what it does not:

- **hexvero reads more of a small Electron application and reports far less that is wrong**, on code neither tool had seen. It still misses a lot there: 31 of 72 channels and 21 of 33 window settings. The misses are idioms it does not follow yet, listed in [PROGRESS.md](PROGRESS.md).
- **REA's 30 false endpoints are mostly one decision**: it lists `store.get("key")` and similar calls as network endpoints. Read the other way, as storage, its row becomes 9 / 33 / 3 for endpoints and 30 / 21 / 9 for storage keys. Both readings are in the summary.
- **Native call paths need no extra install beyond radare2 or rizin** in hexvero; REA 6.4.0 has no provider for either. Through radare2 hexvero answered all 70 path questions of the corpus correctly, including paths that run through tail calls and paths that do not exist; through rizin 68, the two misses being a jump to an import that rizin does not list as a function.
- **The fixed cost of an MCP session** is the one cost that does not depend on the input: `tools/list` was 13.4 KB for hexvero's 15 tools at the measured commit (13.7 KB now) and 1.95 MB for REA's 170 (1.77 MB with its compact profile).
- **Per question an agent receives less from hexvero, and gets names**: 15 to 21 KB over MCP for the channels, settings or endpoints of one application. REA's summary is 24 KB but holds counts without names; its complete answer is 1 to 6.5 MB, which for the three hold-out builds exceeded REA's own response budget, so the export file is the way that works.
- **Timings are not compared.** All runs were taken on a busy machine (load 6 to 77 on 8 cores). The raw times are published; no conclusion is drawn from them.
- **This is a small corpus**: three Electron applications of a few hundred lines and three C programs for one platform. It says nothing about large real applications, where REA parses everything and hexvero reads in batches; nothing about dynamic analysis, devices, firmware or the engines REA drives, which hexvero does not attempt; and nothing about how well an agent solves a task with either tool. No agent experiment was run.

Use REA when you need Hopper, IDA, JEB, Android devices over adb, browser capture, saved network captures, firmware, or evidence ids with source ranges for every fact. Use hexvero for the first look, for agents with small context windows, for call paths through radare2 or rizin, and for a UI.

<a id="how-it-works"></a>

## How it works

```text
packages/core     parsers (formats/*), JavaScript scanner, Session (targets, collections, paging, export), engine adapters
packages/mcp      McpServer with 15 tools over one Session
packages/server   loopback HTTP API + static hosting for the UI
packages/cli      hexvero command; ships the built UI and the agent skill
packages/web      React + Vite UI
```

Every parser returns facts plus `findings` and `limitations`. The Session flattens an analysis into named collections and pages them; CLI, MCP and HTTP are thin adapters over the same calls. Analyses run in a worker thread with a timeout and a heap cap. Tests build their fixtures byte by byte (`packages/core/test/fixtures`), so the suite runs anywhere in seconds. See [docs/ARCHITECTURE-PLAN.md](docs/ARCHITECTURE-PLAN.md).

## Contributing

```bash
npm install && npm run check      # typecheck, lint, format, unit tests, shape rules
npm run e2e                       # the four user flows on real inputs (compiler and engines if installed)
node packages/cli/bin/hexvero.js analyze /bin/ls
```

Adding a format is one parser in `packages/core/src/formats/` plus one byte-built fixture test. Findings need a confidence, anything skipped becomes a limitation, every list is paged. [CONTRIBUTING.md](CONTRIBUTING.md) has the rules the review workflow enforces; issues labelled `good first issue` are sized for an afternoon. Found a wrong or missing fact? [Open a bug report](https://github.com/maximilianfeix/hexvero/issues/new?template=bug.yml) with the `hexvero doctor` output and, if you can share it, the file.

If hexvero told you something useful about a file, a star helps other people find it.

## FAQ

<details><summary><b>Does hexvero run or upload my files?</b></summary>

No. Targets are parsed as bytes; nothing is executed. The UI server binds to 127.0.0.1 with a per-session token and rejects other hosts. There is no telemetry and no network call anywhere in the code base. When you use hexvero through a cloud-hosted agent, the results that agent requests are sent to its model provider like any other tool output; keep that in mind for files you would not share.

</details>

<details><summary><b>Is this a decompiler?</b></summary>

Not by itself. Built-in analysis gives you structure, symbols, strings, imports, metadata and hardening facts. For disassembly and pseudocode, install radare2, rizin or Ghidra and use `hexvero provider` or `hexvero calls`.

</details>

<details><summary><b>Is "static" the same as "safe"?</b></summary>

Parsing a hostile file is still processing attacker-controlled bytes. hexvero bounds every parser (sizes, counts, depths, worker timeout and heap cap) and its tests include truncated and oversized inputs, but no parser is proven safe against every crafted file. Treat results as evidence, not as a verdict.

</details>

<details><summary><b>What about Windows?</b></summary>

Parsers, the CLI, the MCP server and the UI run on Windows (CI runs the test suite on Windows and macOS). Engine process handling is tested on POSIX only.

</details>
