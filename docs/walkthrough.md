# A walkthrough of hexvero

What each step of a release review shows, on the two example builds that `npx hexvero demo`
copies (NotesDesk 1.4.0 and 1.5.0, generated by `scripts/build-examples.mjs`, not a real
product). Every block below is a real run of hexvero 0.9.9 under `npx`, in an empty directory.
Moved here from the README after 0.9.9.

The commands hexvero suggests (`Next`) are written the way you started it: `npx hexvero …` under
npx, `hexvero …` after `npm install -g hexvero`.

1.5.0 adds `checkUpdate`, a member pages can call, whose handler at `main.js:30` fetches a new
host. `shell:open` exists only in 1.4.0, but 1.5.0 registers channels whose names come from an
environment variable at `main.js:33`, so hexvero reports it as `?` unknown, not as removed.

## 2. The change, with the evidence of both builds: `compare`

```bash
npx hexvero ui --demo --open
npx hexvero compare hexvero-demo/notesdesk-1.4.0.asar hexvero-demo/notesdesk-1.5.0.asar --report report.html
```

In the UI every `file:line` opens the lines around it, in the build before and the build after
side by side. `--report report.html` writes the same comparison as one offline page with those
lines (`--report report.md` as Markdown for a review); the same inputs give the same bytes. With
0.9.9 the example's `report.html` is 33,298 bytes. Examples:
[report.html](https://maximilianfeix.github.io/hexvero/demo/report.html),
[report.md](https://maximilianfeix.github.io/hexvero/demo/report.md).

## 3. The same comparison as a release gate: `check`

```text
$ npx hexvero check hexvero-demo/notesdesk-1.4.0.asar hexvero-demo/notesdesk-1.5.0.asar --policy hexvero-demo/policy.json
hexvero check fail: the policy is violated
  before notesdesk-1.4.0.asar · after notesdesk-1.5.0.asar · policy policy.json

  ✗ new-interface-member  notesdesk.checkUpdate  new · fail
      New interface member notesdesk.checkUpdate is exposed to pages.
      @ b: preload.js:9, handler main.js:30 · link direct · fingerprint 40aa15f76bfd9988f9302d187c03c61d
  ✗ new-external-host  updates.notesdesk.example  new · fail
      New external host updates.notesdesk.example, not in the allow list (https://updates.notesdesk.example/latest.json).
      @ b: main.js:30 · literal · fingerprint 68312dcec55422c3b8affec165b21b83

  Accept what is there now: add --baseline <file> --update-baseline, or a suppression with the fingerprint and a reason in the policy.
$ echo $?
3
```

The policy is JSON, data only ([`examples/policy.json`](../examples/policy.json),
[schema](policy.schema.json)) with five rules: `new-interface-member`, `new-external-host` (with
an `allow` list), `window-more-permissive`, `new-bridge-exposure` (a privileged object such as
`ipcRenderer` or `fs` handed to pages as it is) and `fuse-weakened` (a packaged build's fuse moved
to its less safe state, ASAR integrity coverage lost, or the Electron line past its end of
support). Exit `0` pass, `1` technical error, `2` usage or
invalid policy, `3` violated, `4` not decidable: an unknown (a host built at run time, an
unreadable bridge, an app read in part) is never a pass under `"unknown": "fail"`.
`--baseline file --update-baseline` accepts what is there once (the same run then exits `0`);
suppressions take a reason and an expiry date. Output as text, JSON, Markdown or SARIF 2.1.0. The
GitHub Actions workflow, with a least-privilege SARIF upload: [ci.md](ci.md). Over MCP:
`hexvero_check`. Every rule in detail: [cli.md](cli.md#release-policies-hexvero-check).

`hexvero init` writes a starting policy with the hosts a build already talks to:

```text
$ npx hexvero init hexvero-demo/notesdesk-1.4.0.asar
✓ wrote .hexvero/policy.json: every rule at fail, unknown: fail, 2 host(s) of hexvero-demo/notesdesk-1.4.0.asar allowed
    api.notesdesk.example
    telemetry.notesdesk.example
  hexvero-demo/notesdesk-1.4.0.asar checked against itself: pass: no new finding at level fail
  next: npx hexvero check <before> <after> --policy .hexvero/policy.json
```

Checking the pair against that policy fails on the same two findings as above (exit `3`).


A filled dot is a fact read from the file, a hollow dot an inference from a pattern;
`@ main.js:14` is where it was read. Settings are reported as written, never as assumed Electron
defaults. Where a part of an address is computed at run time, `${…}` stands for that part (in
this build both addresses are read whole). The `windows` collection puts each window's
`nodeIntegration`, `contextIsolation` and `sandbox` side by side as `true`, `false`, `computed`
or `not written` and says what follows from them together; a value that rests on Electron's
default for the version in `package.json` is marked `default on` / `default off`. The rules and
their sources are in [electron-findings.md](electron-findings.md). The IPC finding is a filled dot
only when every IPC-shaped call could be traced; otherwise the limitations name the calls that
could not, with file and line.

not reported as changed. Without a list name, `compare` counts the differences in every list both

The `interfaces` list joins each preload member to the windows that load it and to the
main-process handler on its channel, with file and line, and says how the link was made
(`direct`, `resolved`, or `unresolved`/`unknown` with the reason). Walkthroughs:
[Electron interface map](use-cases/electron-interface-map.md),
[release interface diff](use-cases/release-interface-diff.md).

Nothing is ignored by default; code that only moved in a native binary is counted as
`relocated`. Windows are matched by the variable they are assigned to (`win`), so adding a window
does not mis-pair the others. An item found on one side only is `added` or `removed` only if the
other side read the file it sits in and compared its whole list; otherwise it is `unknown` (`?`),
with the reason.

The same commands take a packaged build in place of an `.asar`: a macOS `.app`, a Windows or
Linux install directory, or a release ZIP (see
[cli.md](cli.md#packaged-builds-app-install-directories-zip)).

## 6. The web UI

```bash
npx hexvero ui --open
```

![hexvero UI: the overview of an Electron app, each finding with its confidence and source line](screenshots/ui-overview.png)

![hexvero UI: the source lines around a change, the line it was read from highlighted](screenshots/ui-source.png)

![hexvero UI: findings with their source lines, and the hex viewer decoding a selected byte](screenshots/ui-hex.png)

Starts a loopback server with a per-session token and opens the browser. **Compare** puts two
open builds side by side: the window settings to review, every change per list with the file and
line it was read from (each opens the source lines around it), a filter, the counts of every
list, what was not established, the evidence of a row with the lines of the build before and
after side by side, and a Markdown report download. **Release gate** at the end of the review
checks the pair against a policy (prefilled with the example policy, editable in place): pass,
fail or incomplete in words, each finding with its source lines and fingerprint, and a SARIF or
Markdown download of the result ([recording](demo/ui-review.mp4)). `hexvero ui --demo --open`
starts with the example builds; the start screen offers them too. Drop a file anywhere, or type a
path on your machine. Each target gets a verdict line, a fact sheet, findings with confidence,
the limitations, and one tab per collection that actually exists. The hex viewer loads windows on
demand, decodes the selected bytes as u8…u64/f32/f64 in both byte orders and follows the arrow
keys. Electron apps get a layered module graph and an interface map (window → preload member →
channel → main-process handler). Dark and light themes, keyboard navigation throughout
(`⌘O`/`Ctrl+O` open, `/` filter, arrow keys on tabs, hex and graph), phone layout.

## 7. Other kinds of target

You downloaded a binary, an Electron app or an APK: hexvero says what it is, what it exposes and
where the evidence is, and suggests what to look at next. The formats, a native example and the
optional engines are in [formats.md](formats.md); letting a coding agent do the investigation is
in [mcp.md](mcp.md).

## How it works

```text
packages/core     parsers (formats/*), JavaScript scanner, Session (targets, collections, paging, export), engine adapters
packages/mcp      McpServer with 16 tools over one Session
packages/server   loopback HTTP API + static hosting for the UI
packages/cli      hexvero command; ships the built UI and the agent skill
packages/web      React + Vite UI
```

Every parser returns facts plus `findings` and `limitations`. The Session flattens an analysis
into named collections and pages them; CLI, MCP and HTTP are thin adapters over the same calls.
Analyses run in a worker thread with a timeout and a heap cap. Tests build their fixtures byte by
byte (`packages/core/test/fixtures`), so the suite runs anywhere in seconds. See
[ARCHITECTURE-PLAN.md](ARCHITECTURE-PLAN.md).
